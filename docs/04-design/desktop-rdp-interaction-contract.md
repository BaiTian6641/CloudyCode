# Standard RDP with desktop interaction

**Decision D15 — user clarification, 2026-10-15.** Cloudy Desktop is an Android-packaged **desktop/laptop RDP client** for Googlebook. It must interoperate with standard compatible RDP servers on Linux, Windows and macOS without Console or a Cloudy host agent. Use established engines and open-source clients as implementation and interaction references. The current FreeRDP diagnostic is a qualification application; this contract is product scope, not a claim that these workflows are implemented.

Read the [backend boundary](../02-architecture/remote-desktop-backends.md), [authentication and local credential security](../02-architecture/rdp-authentication-security.md), [desktop platform contract](../03-platform/googlebook/desktop-application-contract.md) and [terminal interaction contract](desktop-terminal-interaction-contract.md). Termius remains the SSH/SFTP UX reference; RDP has its own input, session and authentication semantics.

## Host scope and compatibility

The client runs on Googlebook. Linux, Windows and macOS are **remote host targets**, not additional native Cloudy client ports. Record support by server/version, OS/session/compositor, authentication method, graphics and negotiated input capabilities. A generic OS checkbox cannot describe that matrix.

| Host target | Standard server route | Qualification and honest limits |
| --- | --- | --- |
| Linux | Maintained RDP server such as KRdp, GNOME Remote Desktop or xrdp, with its actual desktop/session backend | Current Ubuntu/Wayland workstation is primary. KRdp diagnostics establish bounded video/NLA and controlled keyboard-marker delivery with one case mismatch through a subsequent user-consented portal session; the earlier Plasma target-input failure remains retained. Physical/relative input acceptance remains pending. An xrdp virtual Xorg session is different from the logged-in Wayland desktop. Verify server consent, login/lock/headless and relative-input behavior separately. |
| Windows | Enabled Microsoft Remote Desktop host on a supported edition, or another specifically qualified RDP server | Record exact Windows edition/build, account/domain policy and session behavior. Windows Home cannot host Microsoft's built-in RDP service. No Windows device is currently qualified. Parsec remains the user's temporary access option, with its own explicit profile. |
| macOS | A separately selected and qualified standards-compatible RDP server, if one meets maintenance, security and session requirements | Apple's documented Screen Sharing/Remote Management route is VNC-compatible; it does not establish an RDP endpoint. Keep macOS RDP as a host objective with server feasibility unresolved. A qualified VNC or streaming profile is a separately labeled alternative, never an RDP pass or silent protocol substitution. |

Sources checked 2026-10-15: [Microsoft RDP hosting prerequisites](https://learn.microsoft.com/en-us/windows-server/remote/remote-desktop-services/remotepc/remote-desktop-allow-access), [Apple Screen Sharing](https://support.apple.com/guide/mac-help/turn-screen-sharing-on-or-off-mh11848/mac). The macOS RDP conclusion is a project dependency assessment from the documented VNC route; it does not assert that no third-party RDP server can exist.

## Desktop input and window behavior

| Interaction | Required behavior |
| --- | --- |
| Direct pointer | The visible remote point follows the physical pointer through the actual content scale/letterbox transform. Primary, secondary and middle buttons, wheel axes and modifier chords have explicit native mappings. Outside-content coordinates cannot accidentally click a remote edge. |
| Selection and drag | Normal mouse press/drag/release, multi-button chords and remote context menus work without long-press, a mobile key row or an overlay trackpad requirement. Trackpad gestures are mapped only where Android supplies supported events. |
| Keyboard | Focused native profile/password fields keep native editing. The remote surface forwards qualified physical key/scancode/layout combinations and repeat behavior; OS-reserved shortcuts remain local. Expose deliberate local/remote shortcut routing, a shortcut reference and menu equivalents. |
| IME | Native composition/preedit stays local until committed, with a single delivery path. Remote Unicode/key-layout capabilities determine supported text; never duplicate a commit through both physical and text paths. Reject malformed text safely and qualify non-Latin/supplementary input with the actual server. |
| Clipboard | Show direction, format and session scope. Default off until deliberately enabled per profile/session; separate one-shot actions from continuous redirection. Native-field paste is distinct from remote clipboard or keystroke injection. Never fall back to typing clipboard content without an explicit action. |
| Window controls | Native caption and system controls retain their role. Resize, maximize, restore, narrow desktop tiling and fullscreen expose the current remote resolution/scale. A server resize must not silently create a different session. |
| Capture and escape | A visible capture indicator and local Release input action remain available. Reserve a discoverable, remappable release chord, initially Ctrl+Alt+Shift+R, checked against OS handling on the device. This chord is local and never forwarded; menu/focus-loss release remains available if the OS intercepts it. |
| Focus/lifecycle | Track only keys/buttons whose downs this session accepted. Release them when focus/capture is lost, a dialog opens, the session disconnects or ownership changes. No stale held physical button may rearm a remote drag on return. A lost connection can prevent delivery of a release: clear local state, report the interruption and reconcile on explicit reconnect without replaying clicks. |

All local commands must work with keyboard and pointer. Accessibility focus, native font scaling, visible focus and meaningful labels remain required. Touch accessibility remains supported by Android where available, but mobile interaction patterns do not define desktop workflows.

## Relative mouse for 3D applications

Relative mode is a required capability for qualified 3D/CAD workflows. **Capturing the local pointer and sending genuine negotiated relative RDP events are separate requirements.** Absolute coordinates with recentering are not accepted as proof of relative mode.

1. Start in normal absolute mode. Enter relative mode through an explicit session action or a remembered profile preference that still requires a focused, connected surface and available local capture. Show the mode and release command before capture.
2. Use Android's public pointer-capture APIs. Confirm capture through its callback rather than assuming a request succeeded. Use the documented captured-event representation for the device, process historical samples in order and avoid double-counting movement from multiple axis representations. Track physical mouse and trackpad capability separately.
3. Require the RDP engine's negotiated relative-input capability. Send signed relative deltas through its existing protocol implementation, preserve sub-unit remainder if conversion is needed and split out-of-range deltas into representable events without changing their total. Never clamp a large delta and silently lose movement. Preserve button/key transition ordering and bound queue growth.
4. Do not multiply relative deltas by framebuffer fit/zoom scale. Any sensitivity setting is explicit, reversible and measured; pointer acceleration/raw-device guarantees cannot be inferred from Android capture. Motion coalescing may preserve summed deltas, but must not reorder transitions or drop releases.
5. On rejected capture, missing server capability or actual application incompatibility, show which boundary failed. Offer an explicit return to absolute mode or another separately qualified desktop backend. A visible unavailable mode is honest behavior, not completion of the 3D requirement for that combination.
6. Release capture and held input on focus loss, native dialogs, disconnect, task closure and the release action. Reacquisition needs a fresh focus/ownership decision; a background surface cannot seize the pointer. A different task/window must remain operable.

Android provides `View.requestPointerCapture`, `onPointerCaptureChange`, `onCapturedPointerEvent`, `hasPointerCapture` and `releasePointerCapture` from API26. `MotionEvent.AXIS_RELATIVE_X/Y` exist from API24 and carry per-sample motion; their availability alone does not establish device behavior. The [Android mouse guide](https://developer.android.com/develop/ui/views/touch-and-input/gestures/movement#pointer-capture) and [MotionEvent reference](https://developer.android.com/reference/android/view/MotionEvent) are the platform contract.

The pinned [FreeRDP 3.32.2 input API](https://github.com/FreeRDP/FreeRDP/blob/97eff6ddfbbfaa8e42a126d362686bd001ff8bdc/include/freerdp/input.h) already implements relative RDP events and negotiation. Require negotiated `FreeRDP_HasRelativeMouseEvent` and the standard `freerdp_input_send_rel_mouse_event` route. Microsoft's [Input Capability Set](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpbcgr/b3bc76ae-9ee5-454f-b197-ede845ca69cc) and [relative pointer event](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpbcgr/9af47964-8bfc-4f43-8a15-4339a89833fa) define that route. The pinned [client helper](https://github.com/FreeRDP/FreeRDP/blob/97eff6ddfbbfaa8e42a126d362686bd001ff8bdc/client/common/client.c) can instead use the optional AINPUT channel or accumulate relative movement into absolute coordinates. Its `freerdp_client_use_relative_mouse_events` result includes AINPUT availability. Neither that helper boolean nor local SDL capture establishes standard relative support. If AINPUT is later selected, identify and qualify it as a separate extension; prohibit silently passing the absolute branch off as relative mode. Cloudy's 0.1.4 diagnostic now includes a bounded typed relative JNI/queue/view adapter. Its full native build, Android compilation/Lint, 36 JVM tests and actual-source queue device test pass. It sends signed standard relative events only and keeps wheel on the existing wheel-only route; no AINPUT or absolute movement fallback is used. A real session reports negotiated standard relative support and a confirmed framework capture callback. Those observations do not establish physical movement, host relative-event consumption or 3D behavior. Do not replace the engine or invent a custom remote input protocol to fill that boundary. See the exact protocol/source mapping in the [API tracker](../03-platform/googlebook/api-tracker.json) under API06 and API45.
