# Native app appearance and density

The current P1-S2 increment supplies real per-app System/Light/Dark appearance and Comfortable/Standard pointer/Compact pointer density settings. Console and Desktop each own their preferences and process state; opening another window observes the same owning-app state. This does not change the other product, device settings, credentials, host profiles or session authority. The original **0.1.6/code7** checkpoint established this behavior; current installed products are **0.1.13/code14**, with the [outcome-semantics follow-up](../../qualification/results/P1-S2/2026-10-16-display-outcome-accessibility.md) below. The [qualification record](../../qualification/results/P1-S2/2026-10-16-native-display-settings.md) binds strict compilation, four zero-issue Lint reports,12 actual Android cases and six leader-inspected Console viewport captures. Full P1-S2 remains in progress.

`CloudyDisplaySettings` derives the supported package and checks its UID, rejects the originally supplied device-protected context before application normalization, and opens credential-encrypted app-private `cloudy-display-v1` SharedPreferences. Its only interpreted fields are `appearance` (`SYSTEM`, `LIGHT`, `DARK`) and `density` (`COMFORTABLE`, `STANDARD_POINTER`, `COMPACT_POINTER`). Missing fields default to `SYSTEM` and `COMFORTABLE`. Invalid present values use a safe default for that field and show a recovery notice; reading does not delete or repair it. Unknown fields are retained. An explicit selection commits only its own enum field, so a stale window does not overwrite a different field from an old whole-settings snapshot. The existing product backup exclusions remain applicable.

One app-process owner publishes immutable observable state. A bounded serial executor performs loading and synchronous `Editor.commit()` off the main thread; completion publishes state on the main thread. Choices are disabled until ready and during loading/saving. Queue rejection reports that the operation was not submitted, and Close remains available. There is no service, polling, cross-app storage or multiprocess preference protocol. [SharedPreferences (G213)](https://developer.android.com/reference/android/content/SharedPreferences) and [Editor (G214)](https://developer.android.com/reference/android/content/SharedPreferences.Editor) define the framework boundary.

A failed commit can leave changed process-memory preferences despite unconfirmed disk persistence. The UI shows available runtime values and a persistent-in-process uncertainty notice; Refresh, another wrapper instance or a cached read does not prove a disk save. Only a later explicit successful commit resolves that uncertainty. No mutation is automatically replayed. The uncertainty flag is process state, not a durable crash-recovery receipt; a future process reads whatever preferences the framework actually loads. This lightweight presentation store is not the identity/trust store.

`CloudyAppTheme` observes the owner and supplies preferences to `CloudyTheme`; explicit choices recompose app content without requesting Activity recreation. `SYSTEM` evaluates `isSystemInDarkTheme()` from the current Android configuration. Density metrics use a composition-local provider, with existing color-role and typography definitions retained. Body text remains **14sp/20sp line height**, and no platform density, font scale or `LocalDensity` override is introduced. Current roots include workspace, vault, profiles, SSH trust and display settings. [CompositionLocal (G216)](https://developer.android.com/develop/ui/compose/compositionlocal) supplies scope, rather than any shared daemon.

Nominal sizes are minimum layout inputs, not fixed rendered heights or permission to shrink interactive targets. Material retains its native minimum interactive sizing; settings radio rows explicitly retain at least48dp. Text and multiline content can grow. Existing canonical field/button/chip/dialog radii remain unchanged. [Compose accessibility defaults (D12)](https://developer.android.com/develop/ui/compose/accessibility/api-defaults) still require target/overlap review, and selecting compact density does not certify physical pointer or accessibility behavior.

The facade updates the owning Activity's transparent system-bar styles using `SystemBarStyle.auto` with effective content darkness. That API was added in Activity1.8.0 and is available in the selected **1.13.0** dependency; moving reference documentation deprecates it in **1.14.0-alpha03**, which is not adopted by this change. Review its replacement when upgrading. Native captions, splash/launch appearance and IME remain controlled by Android; this increment does not promise to recolor them or clear secure flags. [SystemBarStyle (G215)](https://developer.android.com/reference/androidx/activity/SystemBarStyle) records this version boundary. `UiModeManager.setApplicationNightMode` (API31) was reviewed as an alternative but is not called; its persistent configuration override and component lifecycle effects are outside this Compose-only choice. No reset API or `MODE_NIGHT_AUTO` follow-system equivalence is assumed. [UiModeManager (G217)](https://developer.android.com/reference/android/app/UiModeManager).

The settings Activity uses native selectable radio semantics, safe-drawing and IME insets, and scrolling. Full P1-S2 remains in progress: the complete component catalog, rendered semantic contrast, keyboard/pointer/focus behavior, narrow/short tiled windows, scale changes and engine-backed working-area geometry still require their own qualification. This increment does not freeze every native component or advance remote capability gates. See the [P1 phase](../05-delivery/phases/p1-foundation.md).

## Bounded rendered follow-through

At font scale1.0, the six actual Console captures show seven control semantics heights of48dp Comfortable,40dp Standard and36.31dp Compact; label bounds remain20.31dp. The32dp Compact value is a minimum, not a forced height. These are clipped semantics bounds and do not measure interactive hit targets. Both themes/all three densities retain the native draft/selection and window identity. Captures cover the local workspace only; settings, protected dialogs and full component/physical-input acceptance retain separate gates.

Tests restored effective System/Comfortable defaults through explicit successful commits. Both previously absent preference XML files now contain those explicit defaults. This is value restoration, not identical initial file/key representation; no production settings file was deleted.

## Outcome announcements

The existing localized display outcome text now sets `LiveRegionMode.Polite`. Progress and the separate persistent recovery explanation remain ordinary readable content, avoiding competing live regions. The official [Compose semantics guide](https://developer.android.com/develop/ui/compose/accessibility/semantics) (G248/API56) recommends polite announcements for important changing notices and discourages frequent updates. Visible layout, tokens, native radio selection and persistence are unchanged.

The0.1.13 follow-up passes one actual owning-app settings method per product after real preference commits, including Saved text, Polite semantics and controlled Activity recreation. Both complete typed preference baselines are restored. These framework semantics checks do not establish physical screen-reader speech or settings-screen visual/keyboard acceptance.
