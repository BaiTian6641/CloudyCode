## G1 — native APK → VM authenticated binary transport

**Claim established:** code in the installed APK under its real UID reached the
existing Terminal-forwarded control endpoint with an authenticated HTTP/1.1
Upgrade and exchanged full-duplex binary frames. The endpoint was
`127.0.0.1:14509` (sessiond), not 14500; no X server or display cookie was in the
path. This does **not** prove the production 14500 X11 transport; C2.5 tests that
separately. **Environment:** physical device; Terminal VM running; adb-shell and
host results are separate facts and were not used as the app-UID proof.

Probe launch (sanitized; the short-lived probe token is provisioned only in the
VM and passed at launch, never committed):

```sh
adb shell am force-stop dev.cloudy.x11
adb shell am start -n dev.cloudy.x11/.ui.X11AppsActivity \
  --ez probe true --es probe_token '<short-lived>' --ei probe_port 14509
```

## C2.4 — Cloudy Code backend/extension-host environment

**Claim established:** the live `cloudy-backend.service` (code-server) now starts
with the VM-wide display environment, so its integrated terminals, tasks,
extension hosts and extension-host children inherit it. The live unit is
`/home/droid/.config/systemd/user/cloudy-backend.service`; the applied drop-in is
`cloudy-backend.service.d/90-cloudy-x11.conf`:

```ini
[Service]
Environment=DISPLAY=:99
Environment=XAUTHORITY=/home/droid/.local/share/cloudy/Xauthority
```

After a controlled backend restart (`MainPID 54077`):

```
DISPLAY=:99
XAUTHORITY=/home/droid/.local/share/cloudy/Xauthority
```

Source changes: `tools/device/cloudy-setup.sh` writes the drop-in; the reh-web
`start-backend.sh` exports the same values; `cloudy-x11-setup.sh` installs the
drop-in and restarts an active backend.

**Not yet proven:** a fresh UI-driven integrated terminal and an actual
extension-host GUI child were not exercised in this run. Inheritance is from the
verified backend environment; the UI/extension fixture remains a C2.4 follow-up.
A backend restart closes existing workbench connections; the user must reconnect.

## C2.5 — 14500 raw X11 tunnel bridge

**Claim established:** the harness connected only to the existing forwarded
14500 token proxy, authenticated, upgraded to `/x11-tunnel`, received the
versioned bridge configuration, and drove X11 streams over the private VM Unix
tunnel to a local Xvfb. Wrong credentials/Upgrade and wrong X11 auth fail closed;
there is no TCP X11 listener. **This is a bridge/harness result**, not the native
Android engine and not a per-window result.

Topology used: `X client on :99` → `cloudy-x11-vm` Unix proxy
(`/home/droid/.local/share/cloudy/x11-tunnel.sock`) → 14500 bridge →
`tunnel-test.py --via-proxy` → `Xvfb :98` (X.Org 21.1.16). The Xvfb/harness are
explicitly the test upstream, not the product renderer.

Harness log:

```
proxy connected display=:99 generation=00b462446d635dd5 limits=1048576/64/16777216
tunnel connected
```

`DISPLAY=:99 XAUTHORITY=$BASE/Xauthority xdpyinfo` (through the harness):

```
name of display:    :99
version number:    11.0
vendor string:    The X.Org Foundation
vendor release number:    12101016
X.Org version: 21.1.16
...
```

Negative checks:

| Check | Observed |
|---|---|
| Wrong tunnel cookie on 14500 | `HTTP/1.1 403 Forbidden` |
| Valid cookie, wrong Upgrade | `HTTP/1.1 400 Bad Request` |
| No display cookie | `Authorization required, but no authorization protocol specified`; `unable to open display ":99"` |
| Wrong display cookie | `Invalid MIT-MAGIC-COOKIE-1 key`; `unable to open display ":99"` |
| TCP X11 listeners | none |
| Unix tunnel | `/home/droid/.local/share/cloudy/x11-tunnel.sock` listening |
| Bridge config | one `CLOUDY-X11-CONFIG 1` line; cookie value not recorded |

The VM proxy now sends `OK <cookie>` from `$BASE/x11-cookie`; the bridge rejects
the legacy bare `OK`. The cookie is extracted from the binary Xauthority by the
installer; no `-ac` is used. The bridge's 101 is preceded by a verified upstream
handshake. The byte pump has a 600 s idle bound.

**Known limitation:** the bridge config carries the display cookie over the
local HTTP channel; production confidentiality/peer-identity remains a security
gate. The Xvfb path does not prove engine rendering, accepted-fd authentication,
window discovery or per-window Android hosting.
