# Googlebook platform review — 2026-10-16

## Scope and evidence boundary

Reviewed original plan §§2, 5, 6, 7, 10 and 12 against retrieved Google/Android documentation. This report supports Stage 0, networking, desktop, storage, lifecycle and release gates; it does not certify an implementation. **No physical Googlebook, APK, USB device, VM kernel or shared filesystem was tested.** All source accesses below occurred **2026-10-16**. DOC means documentation, SOURCE means upstream implementation rather than a shipping guarantee, DESIGN means proposed engineering, UNKNOWN means not established, and ROADMAP means announced future work. Search snippets are discovery evidence only.

The existing architecture is substantially consistent with current documentation: retain the original upstream workbench, Android presentation, built-in Debian execution, user-managed extensions and default `wsl_usbip_desktop`. A successful browser demo, serial API enumeration, or emulator run cannot replace the mandatory ordinary-APK and ESP32-S3 serial/JTAG plus external-adapter gates.

### Search coverage and unavailable claims

Searches included `site:developer.android.com Googlebook Terminal Linux preview API serial 37`, `site:developer.android.com Googlebook Terminal third-party API VM control WebView local network permission`, and `site:developer.android.com "WebView" "local network" "permission"`. Results identified official Googlebook overview, Terminal preview, ADB debugging, and ordinary WebView local-server development guidance. **No documented ordinary-third-party API to control this existing Terminal VM, execute guest commands, acquire its lifetime reference or grant its folders was found.** This is a bounded negative search finding, not proof such an API cannot ever exist.

The WebView search returned a Portuguese search snippet explicitly claiming host-app permission inheritance. Actual retrieval of [that translated page](https://developer.android.com/privacy-and-security/local-network-permission?hl=pt-br), like the English page, **did not contain that sentence**. Do not cite the stale snippet as fresh DOC evidence. The retrieved guide supports the general all-networking-APIs restriction; exact WebView/VM route behavior remains a device gate. All registry pages were reachable; no missing source was silently replaced by a guessed API.

## Recommended corrections and additions to the original plan

1. **§2:** retain Debian/forwarding/dual-grant findings, but qualify “current public serial API” as *documented API 37 surface, not guaranteed Googlebook availability*. Preserve the existing alternative-graphics versus launcher-integrated-GUI distinction. Record Terminal preview date explicitly; roadmap must never become a dependency marked implemented.
2. **§§2.2, 5.7:** replace the assertion that the freshly reviewed R49 explicitly states WebView inheritance with the exact retrieved all-APIs rule and the snippet/body discrepancy above. Add the target 36 versus 37 migration matrix, denied/revoked states, potential TCP timeouts and permission-group pregrant. A generic timeout is not proof of stopped VM. Do not request broad LAN permission reflexively if measured supported loopback does not require it.
3. **§§2.3, 10.1, 12.2:** retain user-driven launch/bootstrap as the executable baseline. Treat AOSP action as optional source-based launch discovery, not public command transport. AOSP default-disabled app and unexported service strengthen why a generic manifest cannot identify Googlebook's actual package/behavior. No new hidden API, ADB dependency in normal usage, or replacement VM.
4. **§6:** map desktop acceptance to P19 test IDs, especially triple-click, modifier+pointer selection, discoverable shortcuts, cursor correctness, OS file handler and batch drag/drop. Keep original workbench layout; Compose Navigation 3 examples are not a mandate to rebuild it. Honor caption safe zones and separately test IME composition rather than translating it into hardware key events.
5. **§7:** enforce supported local directory/provider selection and explain Android tree-picker exclusions. Keep bidirectional nonce, hash and semantics probes. Test VM Files provider separately if considered; do not assume it gives the same topology as a host-selected share. Managed-native mode must remain explicitly different from shared-source mode, not a silent pass for a failed sharing requirement.
6. **§§10.2, 12:** enumerate `connectedDevice` manifest/base permissions and qualifying USB permission path. Handle invalid background start and grant revocation without adding unrelated permissions simply to satisfy a service prerequisite. For serial-only diagnostics, first resolve a legitimate service prerequisite; the new serial API is not automatically equivalent to `UsbManager.requestPermission()`.
7. **Release stage:** replace remembered deadlines with the currently retrieved P16/P18/P21 values and re-check before shipment. API 37 compile/runtime support, target SDK policy, developer verification and 16 KB alignment are four distinct decisions. Audit every transitive native library, including exporter/JNI dependencies; do not infer Android ABI/page size from Chrome UA or Debian `uname`.

## Exact device probes and stage acceptance prerequisites

These are **DESIGN instructions for later execution**, not completed checks. Save command output, screenshots, APK hashes, test timestamps and expected/actual result per case; redact credentials. Never populate DEVICE-PASS from this report.

### Stage 0 — identity, APIs and VM lifecycle

- Record host model/OS fingerprint/security patch, `adb shell getprop ro.build.version.sdk`, `adb shell getprop ro.product.cpu.abilist`, `adb shell getconf PAGE_SIZE`, Terminal package/version and installed WebView provider/version (`adb shell dumpsys webviewupdate` where available). ADB is a development probe, not an application runtime dependency.
- In Terminal record `cat /etc/os-release`, `uname -a`, `uname -m`, `getconf PAGE_SIZE`, `id`, `findmnt`, `ip -brief addr`, `ip route`, `systemctl --user is-system-running` and available disk. A missing command or unsupported user service is a finding, not permission to assume success or install packages silently.
- Using an ordinarily signed probe APK, inspect supported SDK service availability and compile the actual API 37 serial calls; enumerate ports, register listener, authorize/open, deny, disconnect and close descriptors. Record returned exceptions and OS dialogs. Do not access hidden serial classes on older releases.
- Start a harmless guest timestamp/heartbeat process. Observe separately: closing one tab, last Terminal window, removing its task, force-stop via user settings, frontend-only death, lock, lid close, sleep/resume, reboot. Record VM boot ID and process ID before/after; a reconnect alone cannot establish process survival. Repeat keep-awake settings with user consent. Never reset a valuable VM for a probe; reset/restore acceptance uses a backed-up disposable environment.
- Acceptance: explicit host/guest identity inventory, known supported launch/bootstrap workflow, and lifecycle dependency documented. Unavailable hardware means this gate remains UNKNOWN, not completed.

### Networking stage — independent client/permission matrix

- Run a reviewed guest HTTP + binary WebSocket echo fixture on one explicit test port (for example 8765), first guest loopback then an explicitly recorded guest interface if forwarding requires it. Record `ss -ltnp`; configure Terminal **Auto-forward all ports off**, then add only the fixture port. Do not assume either bind strategy works.
- Request the identical endpoint separately from desktop Chrome, native APK sockets/HTTP and WebView. Test `localhost`, `127.0.0.1`, `[::1]` and any measured guest address as separate rows; include actual DNS resolution, HTTP body nonce, WebSocket binary hash, error/timeout and elapsed time. No guessed emulator alias is a Googlebook route.
- On applicable host versions, run target-36 and target-37 probe variants with clean permission state; for 37 test grant, denial and settings revocation, and previous Nearby Devices group grant. Android 16 opt-in is a separate diagnostic case, not equivalent to Android 17 enforcement.
- Test native-to-guest and app-loopback-to-WebView separately before introducing the gateway. Test offline Wi-Fi-disabled operation, forwarding removal, backend restart, Terminal close/reopen and concurrent sockets. Test `window.isSecureContext`, worker/service-worker registration and an actual extension webview early.
- From a second LAN device attempt the host's LAN address/test port; repeat for intended IDE/bridge ports. Require inaccessible unauthenticated service and documented bind/forwarding policy. Remove fixture/forwarding when finished.
- Acceptance: ordinary APK authenticated HTTP/WS route and actual renderer requirements pass without root, hidden APIs or developer browser flags. Chrome-only success blocks the APK architecture; a proxy cannot repair absent native reachability.

### Storage stage — two grants, one authoritative directory

- Select a dedicated local host subdirectory via SAF; separately share it in Terminal. Record provider authority, returned URI grant flags, persisted-grant state and guest `findmnt -T <candidate>` output. Discover mapping from user-selected candidates, never a hard-coded `/mnt/...` assumption.
- APK writes random nonce; guest reads exact bytes and writes fresh response; APK verifies response. Hash a binary file both ways. Then test case-sensitive names/case-only rename, composed/decomposed Unicode, executable bits, symlinks, hardlinks, locks, atomic replace, watcher delivery and Git branch/rename operations in a disposable fixture.
- Reopen both applications, reboot, revoke each grant independently, move the directory and exercise provider unavailable/read-only behavior. Require no silent replacement empty directory or success indication for unsaved data. Test reset retention only against explicit backups and separate host-shared from guest-private data.
- Acceptance: mapping and required source-workflow semantics demonstrated; failures select a user-visible documented mode or block the requirement, not silent bidirectional synchronization.

### Desktop and background stage

- Open two actual workbench windows on distinct projects; resize through compact and wide sizes, maximize, minimize, fullscreen, change display scale and move across monitors while editing and while terminal output streams. Verify caption/system buttons never overlap clickable editor controls, workspace identities restore and device ownership is not duplicated.
- Exercise P19 `T-Keyboard_Parity`, `T-Keyboard_Navigation`, `T-Input_Combinations`, `T-Triple_Click`, `T-Hover_Parity`, `T-Multi-Instance`, `T-Drag_Drop_Batch`, `T-File_Picker`, `T-File_Handlers`, `T-Custom_Cursors` and `T-Offline_Support` where relevant. Preserve upstream command behavior and explicitly record OS-reserved combinations.
- Test Ctrl/Alt/Meta chords, AltGr/dead keys, repeat, terminal Ctrl-C versus copy, Chinese/Japanese/Korean composition and commit/cancel during focus switch/resize. Compare final bytes, not merely key-event logs; inspect with a non-sensitive fixture only.
- Start an authorized hardware session from a visible activity; verify foreground notification/stop, background continuation, denial, unplug, revoke, app task removal and failed background restart. No successful software FGS probe certifies USB transfers or the guest's lifetime.
- Acceptance: original workbench interactions pass on physical input hardware, and interruption preserves truthful save/device-operation status. No native substitute editor qualifies.

### Release stage

- Capture exact target/compile/min SDK and every Android ABI, distinct from guest package architectures. Inspect all packaged `.so` LOAD segments for 16 KB alignment, GNU_RELRO end alignment and final APK ZIP alignment using the official P16 procedure; exercise 4 KB/16 KB runtime environments actually claimed. `zipalign -v -c -P 16 4 <apk>` alone is insufficient for runtime correctness.
- Record signed APK clean install, same-key upgrade, rejected wrong-key upgrade, grant/pairing persistence, rollback limits and uninstall behavior. Separately document Play bundle delivery if used; never equate sideload acceptance with Play acceptance.
- Recheck target SDK, native-page policy, regional verification/account/package registration and foreground-service distribution declarations for the actual channel. Do not advertise Play desktop badging until awarded.
- Release remains blocked if any mandatory ordinary-APK route, workspace, upstream-workbench, guest execution, USB/IP, ESP32-S3 serial/JTAG/concurrency or external-adapter evidence is absent. This platform review deliberately provides no such DEVICE-PASS result.
