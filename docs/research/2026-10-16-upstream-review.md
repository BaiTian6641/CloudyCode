# Upstream Code - OSS and browser-backend review

**Access date for every source below:** 2026-10-16. **Reviewed plan:** `../Googlebook_CodeOSS_APK_Engineering_Plan_v2.md`, Sections 1, 3, 6.7–6.8, 9 and 11.5; references R10–R22, R70, R78 and R98.

**Evidence labels:** **DOC** means retrieved primary documentation; **SOURCE** means retrieved source, repository metadata or release metadata; **DESIGN** means a proposed implementation or acceptance requirement; **UNKNOWN** means not established by this review; **ROADMAP** means a future intention, not delivered capability. No APK, backend build, extension, browser workflow or physical hardware was executed or tested. Release availability does not establish target-device compatibility.

## 1. Findings that change the executable plan

1. **Keep the product contract.** An independently branded APK embedding the original workbench, with execution in Google's built-in Debian Terminal VM, is a coherent **DESIGN**. It is not an Electron port or a promise that every Microsoft-distribution feature works. User-selected extensions and the `wsl_usbip_desktop` release profile remain mandatory. Browser limitations do not authorize replacing the workbench, substituting a cloud VM, or dropping native ESP32-S3 serial/JTAG and the separate external adapter.
2. **Do not run an allegedly same-version comparison using the latest candidate releases.** Retrieved latest-stable metadata identifies OpenVSCode Server **1.109.5, published 2026-02-20**, versus code-server **4.141.0, published 2026-10-08, embedding Code 1.141.0**. Their upstream revisions differ. Compare each candidate to its own exact upstream controls; evaluate release freshness separately. A stale common version is permissible as a diagnostic control, not an automatic production choice. This is a concrete correction to Sections 3.2 and 6.7. [E06–E10]
3. **An About-dialog commit is not always the embedded upstream commit.** code-server's build script deliberately puts its **own repository commit** in `product.json` to invalidate caches when its patches change. Resolve the original upstream revision from the pinned `lib/vscode` gitlink, not from the displayed commit. [E09, E11]
4. **Use the right browser control.** Upstream documents both browser-only `scripts/code-web.sh` and browser UI plus Node server `scripts/code-server.sh --launch`. The former cannot serve as the terminal/debugging parity control. Preserve desktop, browser-only and server-backed distinctions in the evidence records; the principal functional web control is server-backed. These are development commands, not a verified production packaging recipe. [E02]
5. **Notebooks cannot be silently optional.** Sections 3.2 and 6.7 currently say “notebooks when supported” and “a notebook when in scope.” For the requested full IDE, require a licensed notebook extension/controller, a real guest kernel and output renderer, with persistence/reconnect/offline tests. Failure is a backend or release blocker, not permission to delete this fixture.
6. **Persistence requires more than a guest extensions directory.** code-server documents settings/keybindings on guest disk but workbench state in browser storage by default. Version 4.141.0 adds `--enable-remote-storage`. Its accompanying secret-storage patch permits persisted values without encryption when encryption is unavailable. The flag is therefore a candidate mechanism to evaluate, not proof of safe complete state persistence. Separate settings/profiles, browser workbench state, unsaved buffers, extension global state and extension secrets. [E05, E08, E13]
7. **Self-hosted webviews are helpful but security-relevant.** code-server's pinned webview patch serves resources locally and changes origin-validation behavior, including matching-hostname shortcuts. This reduces an external-asset dependency but is not an isolation proof. Audit sandbox/CSP, service-worker scope, cookie scope and the APK's main-frame-only native bridge before accepting it. [E12, E18]
8. **Clarify authentication responsibility.** OpenVSCode already offers `--connection-token` and `--connection-token-file`; do not describe it as lacking authentication. Its README explicitly warns about unauthenticated access and the Docker default `--without-connection-token`. code-server defaults to a random password, loopback `127.0.0.1:8080`, and no TLS. Neither default supplies APK pairing, revocation or a secure Googlebook forwarding topology. [E04, E05]
9. **The source/distribution/Marketplace boundaries are real.** Keep the original plan's independent branding, permitted registry and authorized VSIX approach. Manual VSIX installation is not a workaround for licensing restrictions. The optional official Microsoft-server row must remain outside the distributable APK baseline; the actual server license restricts use to Microsoft Visual Studio Code and prohibits combining the software with applications for others to use. [E03, E21–E24]

**SOURCE:** These mappings are available without cloning repositories into this project. **UNKNOWN:** downloaded binary reproducibility, actual target execution, complete dependency provenance and security patch coverage. GitHub marks both retrieved latest releases `immutable: false`; record the resolved commit and artifact hashes, not only the tag name. A published digest establishes expected bytes, not independent publisher authentication.

**DESIGN comparison procedure:**

1. Resolve a candidate's source commit, upstream commit, patch/build-overlay inventory, bundle hash, Node version and architecture. Refuse provenance records that substitute `main`, a moving container tag or an About-dialog label for a resolved source identity.
2. Build clean desktop and server-backed browser controls at **that candidate's** upstream commit, on an appropriate development host. Also use browser-only control to identify worker-only constraints where relevant. Keep separate settings and state directories; never share mutable profile databases between candidates.
3. Fix workspace contents, authorized extension artifacts/versions, fonts, theme, zoom, viewport, locale and trust state. Measure command behavior and guest processes in addition to screenshots. Document extension `engines.vscode` incompatibility instead of silently changing extension versions between runs.
4. If both candidates can be built and maintained on one upstream SHA, that common-source comparison can isolate hosting-patch effects. Achieving it may require a nontrivial rebase; it is not guaranteed by matching major version labels. Do not manufacture equivalence by swapping one server's frontend assets into another bundle.
5. If upstream SHAs differ, run two paired comparisons: candidate A versus upstream A, candidate B versus upstream B. Report cross-version differences separately and assess both against the same required user workflows. Do not score newer upstream functionality as a regression introduced by the older candidate's own patches.
6. Run a separate maintenance/security gate: supported upstream baseline, Node/dependency advisories, patch backlog, reproducible release process, ARM64/x64 assets, recovery migration and demonstrated upgrade/rollback. The observed older OpenVSCode stable is a freshness concern; it does not prove abandonment or a particular vulnerability. A newer branch or maintained rebased build requires its own pin and evidence. A smaller patch count alone never overrides missing fixes or failed workflows.

**Selection recommendation (DESIGN, not a certified winner):** retain both candidates for feasibility, but do not give OpenVSCode's minimal-change objective priority over the observed release-age gap. code-server's current release, local webview assets, proxy support and optional remote workbench storage make it a strong first executable vertical-slice candidate. Its origin/storage/authentication patches require review before production. Prefer OpenVSCode if a sufficiently current maintained build passes the complete suite with less project-owned patching. Escalate to direct Code - OSS serving only for a documented blocker and an explicit maintenance owner, not because upstream lacks any server-capable source.

### 3.2 Source acquisition without replacing the project root

**DESIGN:** This repository remains the APK/integration project. Store source lock records and project-owned patches here; use explicitly configured external cache/build directories such as `${XDG_CACHE_HOME:-$HOME/.cache}/gbcode/upstream/` for downloaded sources and a separate writable build directory. Those paths are proposals, not directories created by this review. An ignored `third_party` checkout is an alternative only if deliberately chosen; never `git clone … .` into the project root or copy all of upstream into it.

At implementation time, acquire by approved HTTPS Git remote, detach at the full resolved commit, and fetch enough history to establish provenance/merge bases. For code-server initialize its recorded submodule rather than retargeting to current upstream. Keep a pristine checkout for controls and a separate patched build checkout. Archives can reproduce a content snapshot but may omit submodules and Git metadata expected by build scripts; pin their hashes and account for those omissions before using them. Pin dependency lockfiles, Node version, package-manager version, compiler/toolchain, architecture, build image and external downloaded extensions/tools. Retain notices and an SBOM for the resulting bundle.

Read the pinned package and scripts before choosing commands. Current upstream documentation uses npm; the resolved 1.141.0 `.nvmrc` says 24.18.0, while the older OpenVSCode development branch describes Yarn commands. Use a capable Linux build host for controls and guest bundles; the runtime guest does not need Electron or a desktop stack. Build output, cache and dependency trees must not become tracked project-root source. Nothing was cloned or built during this research.

## 5. Staged integration and narrow patch strategy

1. **Provenance/license gate.** Resolve candidate and upstream locks as above; inspect maintained release/build inputs and extension artifacts; define independent branding and permitted gallery. Output is an evidence/lock inventory and a reasoned candidate shortlist, not a root-level clone or implementation scaffold.
2. **Authenticated origin vertical slice.** On the actual Googlebook, run one complete candidate bundle inside built-in Debian and reach it from the APK. Explicit authentication is mandatory. Exercise terminal, remote extension host, Markdown webview, a notebook renderer and an independently installed extension immediately; record secure-context, WebSocket, worker and local-resource failures before shell customization. No broad cleartext/security-disable workaround can count as a release pass.
3. **Paired fidelity bake-off.** Run the per-candidate exact-upstream controls and full workflow fixtures. Inventory backend patches plus product/build overrides. Select based on behavior, ongoing maintenance and security review, not screenshots or patch count alone. Failed indispensable workflows block selection.
4. **Thin integration.** Keep backend startup/auth/config/state-layout/health/revision handling in `WorkbenchBackendProvider`. Keep pairing, permission dialogs and OS input/window behavior in the native shell. Use a normal companion extension for Googlebook commands/status/Quick Picks. Adapt real existing remote CLI/window routing rather than inventing a second editor protocol. USB control stays in its separately authenticated broker; normal guest tools/extensions consume real imported devices.
5. **Persistence and isolation gate.** Resolve stable origin and independent windows, migrate state deliberately, verify secrets protection, reject native access from extension frames and previews, and prove offline operation. If code-server remote storage is selected, its plaintext-when-no-encryption path requires an explicit satisfactory storage/security design; merely enabling the flag is not completion.
6. **Upstream maintenance/release gate.** Demonstrate one backend/upstream update and rollback with all workflow fixtures, profiles and required hardware acceptance intact. Recheck source/binary licenses, unresolved advisories, artifact provenance and architecture support. Release only when all mandatory user workflows and hardware gates pass.

**Patch policy (DESIGN):** first reproduce a defect against the matching clean upstream control. Send generic workbench/worker/input defects to `microsoft/vscode`; server-auth/proxy/packaging defects to the chosen backend; Android shell and authorized native-bridge changes stay in this project. Prefer documented configuration and existing extension APIs over patches.
