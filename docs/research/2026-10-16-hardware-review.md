# Hardware review: Android-authorized USB/IP into the built-in Debian VM

Access date for every external source below: **2026-10-16**. Review scope: engineering plan §§8.11–8.21, 10.5, 11.2a, U00/U01/U02 and references R23–R25, R30–R35, R71, R83, R85–R97; optional serial material was checked only to establish its boundary with the default profile.

**Evidence labels:** **DOC** = published primary documentation; **SOURCE** = inspected upstream code, repository metadata, or explicitly attributed maintainer report; **DESIGN** = proposed project requirement/decision; **UNKNOWN** = not established for the target installation; **ROADMAP** = proposed capability, not availability. Source examples and maintainer reports are not independent hardware certification. **No hardware, APK, kernel module, exporter, build, test, or destructive command was run in this review.**

## 1. Decision summary

**DESIGN:** Preserve `wsl_usbip_desktop`: Android owns the permission-granted physical USB device; a userspace exporter sends real USB/IP operations over an authenticated APK/VM route; the existing Debian VM imports through its own Linux VHCI; ordinary guest tools and user-selected extensions operate normally. Preserve the original workbench, native ESP32-S3 USB Serial/JTAG with simultaneous console/JTAG, and a separate external adapter/target. Neither another VM nor a serial shim satisfies this profile.

The architecture is documented in its constituent parts, but target feasibility remains **UNKNOWN**, not a pass. The first decisive experiment is the **actual booted Googlebook guest's functional VHCI import**, in parallel with **ordinary-APK authorized-FD access**. Kernel package names, desktop Debian results, WSL, Termux, Haven's alternative QEMU VM and commercial Android server claims do not establish these capabilities on Google's built-in VM.

The existing plan already gets most boundaries right. Concrete corrections and stronger gates are necessary:

1. **P0 — Production exporter is not selected by the existence of an Android example.** The inspected `usbipdcpp` reset handler returns success without performing a physical reset; error mapping merges distinct backend outcomes. The Rust candidate has blocking/error-discarding physical handlers and no actual in-flight cancellation in its inspected command loop. These are actionable source gaps, not speculative hardware failures (§4).
2. **P0 — Native S3 is not an RFC2217 fallback target.** Current esptool documentation explicitly excludes USB-OTG and USB-Serial-JTAG from remote `rfc2217://`/`socket://` ports because their local USB VID/PID metadata is unavailable. Keep any RFC2217 work separately certified for USB-UART bridges (§6).
3. **P0 — An authorized FD is borrowed, process-local authority, not a new device API.** The Java connection must remain live through native transfer drain and `libusb_close`; wrapping does not gain root, guarantee arbitrary usbfs ioctls, or produce a cross-kernel transferable handle (§3).
4. **P0 — Move a short simultaneous CDC/JTAG experiment into feasibility.** Separate serial and JTAG success can hide the selected exporter's serialization/starvation defect. Keep comprehensive stress and source-debug certification in U02 (§7).
5. **P1 — Reset, configuration and speed need explicit evidence.** An import that succeeds by acknowledging an unperformed operation is not a truthful pass. Record actual speed, descriptor bytes, EP0 behavior, interface claims and re-enumeration; do not silently map unknown to full speed (§5).
6. **P1 — Distinguish two meanings of simultaneous USB.** Native Serial/JTAG's CDC and JTAG can operate together; USB-OTG/TinyUSB and Serial/JTAG share the internal PHY and require different hardware arrangements for concurrent operation (§6).

## 2. Importer: what is established and what is missing

### 2.1 Kernel and authority prerequisites

**DOC/SOURCE:** Linux's USB/IP protocol states: “The device driver for the exported USB device runs on the client machine.” `USBIP_VHCI_HCD` depends on `USBIP_CORE && USB`; core depends on networking. The Kconfig distinguishes importer `vhci-hcd`, physical kernel exporter `usbip-host`, and gadget-side `usbip-vudc`. The proposed APK userspace exporter does **not** require Android's kernel `usbip-host`; Debian still requires a working VHCI importer. [H01–H03]

**DESIGN:** U00.01 must inventory the running release and matching configuration/modules; distinguish `=y`, `=m`, absent and inaccessible. Missing `/proc/config.gz`, `modinfo`, or a module file is not conclusive absence. Conversely, an unrelated `/boot/config-*` or a Debian package installed in the filesystem does not prove the VM booted that kernel. Record live VHCI sysfs, available ports, module-loading policy and authority to perform the eventual attach. Do not infer a supported Google kernel replacement route from guest root.

Required guest facilities are profile-specific:

- VHCI/USB core plus a usable guest TCP socket and attach mechanism.
- CDC ACM for the S3 console's normal `/dev/ttyACM*`; selected USB-UART driver only for a separately selected UART adapter.
- Actual USB device nodes and non-root raw-USB access for OpenOCD/libusb; serial group membership is not sufficient for raw USB.
- HID/hidraw only where the selected external backend requires it; not every CMSIS-DAP transport is HID.
- Correctly scoped udev rules or an explicitly reviewed equivalent if udev is absent; never wildcard world-writable USB nodes.

**UNKNOWN:** The Googlebook model/build's running kernel configuration, module signature/loading policy, supported update path, guest class drivers, ordinary-APK route into Terminal, and VM survival after Terminal closure. None was inspected on hardware here. A positive result in another VM is only a control.

**DOC:** Microsoft's WSL recipe explicitly requires a suitable USB/IP-enabled WSL kernel and may require udev rules. Its numeric minimum kernel version is a WSL-specific support statement, not a rule that any newer Google kernel includes VHCI. VirtualHere's Linux client also uses the built-in Linux USB/IP driver. Neither product removes the importer prerequisite. [H17, H20]

### 2.2 Wire and relay obligations

**DOC:** Device listing uses `OP_REQ_DEVLIST`/`OP_REP_DEVLIST`; import uses a separate TCP connection and `OP_REQ_IMPORT`/`OP_REP_IMPORT`. Successful import retains that connection for submit/unlink traffic. A TCP read or WebSocket message is not a USB/IP message boundary. The documented version is `0x0111`; pin compatibility with the chosen guest tool/kernel rather than inventing a version. [H01]

**DESIGN:** Android may initiate the outer authenticated connection while remaining the USB/IP exporter. The guest relay must remove TLS/WebSocket/multiplex framing and expose the exact USB/IP byte stream on a **guest-owned TCP socket** for VHCI. Do not pass TLS directly to the kernel and do not confuse this local socket FD with the Android physical-device FD.

Native consent shares the **whole approved device with the guest trust domain**. The exporter cannot identify which arbitrary guest extension originated an URB, or universally distinguish harmless reads from programming/reset commands. Keep revocation in native UI; authenticate the outer route and protect the local relay/helper interface too. Loopback reachability alone is not authorization. A helper may attach/detach only owned imports, validate peer credentials/leases/incarnations, and reconcile owned ports; it must not expose arbitrary root shell, arbitrary sysfs writes, or an unrestricted `usbip attach *` sudo rule. These boundaries in §§8.12, 8.17 and 11.2a should remain unchanged.

## 3. Android public authority and native lifetime

**DOC:** USB host support is feature-dependent. `UsbManager` provides discovery, temporary permission and `openDevice`; `UsbDeviceConnection.getFileDescriptor()` is explicitly “intended for passing to native code to access the device.” `claimInterface` is exclusive per physical interface; `force` may disconnect a kernel driver. This is not a guarantee that every selected interface can be claimed under the actual device policy. A closed connection cannot be reused. [H04–H06]

The public Java transfer APIs are bounded:

- `controlTransfer` operates on EP0; synchronous bulk is separate.
- `UsbRequest` supports bulk/interrupt; its documentation explicitly excludes EP0 and requires asynchronous handling for interrupt endpoints.
- Queue success means queued, not transferred. A queued `ByteBuffer` has undefined state until returned by `requestWait`; completion can come from multiple endpoints.
- Java transfer errors are documented as negative failure values, not a complete portable Linux errno taxonomy. Do not manufacture precise stall/timeout/disconnect diagnosis from an undifferentiated result.
- This public API surface has no universal physical bus-reset method and no isochronous `UsbRequest` API. This Java limitation does **not** establish that every authorized native libusb path is incapable of isochronous transfers; native capability remains a separate kernel/backend/hardware question. Isochronous support is not necessary to invent for the initial mandatory profiles. [H06, H07]

**DOC:** `libusb_wrap_sys_device` is available since libusb 1.0.23. Its contract says: “The system device handle must remain open until libusb_close() is called”; `libusb_close` does **not** close that system handle. The temporary wrapped device must not subsequently be reopened with `libusb_open`. It is a borrowed handle unless the application separately duplicates and owns a descriptor. [H09]

**DESIGN:** Pick one explicit ownership model. For a borrowed connection FD: retain the Java connection strongly; prevent new submissions on revoke; cancel and continue servicing native completion events; retire every transfer/callback; release claimed interfaces and close the native libusb handle; only then close the Java connection. If using a duplicated FD, document who closes the duplicate and how revocation invalidates all duplicates; duplication alone neither revokes access nor changes device incarnation. Do not mix Java and libusb request engines against the same connection without an audited single ownership model. Android attach/detach and app/service lifecycle must drive the registry when global libusb discovery/hotplug is disabled.

**DOC/SOURCE correction to R30:** The libusb Android README demonstrates the intended authorized-FD pattern, but also contains historical ABI/build examples and a suspicious sample `libusb_set_option(&ctx, ...)` call. The current initialization API takes `libusb_context *`, not `libusb_context **`, for `libusb_set_option`. Current docs show `libusb_init_context` (since 1.0.27) with `LIBUSB_OPTION_NO_DEVICE_DISCOVERY`, which disables scanning **and hotplug**. Use version-matched headers/API documentation, not a literal copy of that README snippet. Current retrieved API pages identify themselves as libusb 1.0.30. [H08–H10]

**UNKNOWN:** Exact supported usbfs operations on the ordinary APK's granted FD, reset permission, speed reporting, kernel-driver detach, cancellation under detach, multi-interface progress and NDK ABI/page-size compatibility. An API declaration or `libusb_wrap_sys_device` success proves none of those on Googlebook.

### 4.2 Concrete `usbipdcpp` production blockers

The pinned Android example calls `libusb_set_option(nullptr, LIBUSB_OPTION_WEAK_AUTHORITY)`, disables its hotplug path, invokes `bind_host_device_with_wrapped_fd(fd)`, and constructs `asio::ip::tcp::endpoint(asio::ip::tcp::v4(), listen_port)` with default port 3240. **SOURCE:** this is an authorized-FD implementation example and an all-IPv4 listener, not a secure in-process APK integration. Review current libusb option spelling/version and replace the exposed example listener with the product's protected route. [H13]

Pinned `LibusbDeviceHandler.cpp` establishes the following review findings [H14]:

- `tweak_reset_device_cmd` contains a commented-out `libusb_reset_device(native_handle)` and returns `0`. The caller treats zero as handled and emits `create_ret_submit_ok_without_data`. **SOURCE:** success is returned without the physical reset. **DESIGN:** U01.05 must reject or implement the actual operation honestly; a fixture that expects that no-op cannot certify production correctness. Whether the selected S3/external workflow triggers this exact request is **UNKNOWN** and must be captured in the experiment.
- `tweak_set_configuration_cmd` returns `-1`, causing ordinary raw control submission rather than libusb's configuration API. Failed clear-halt/alternate-setting tweaks also fall through into raw control submission. **DESIGN:** audit synchronization of host kernel state, active descriptors, claims and pending transfers; don't equate a raw successful control response with a coherent backend configuration.
- `trxstat2error` maps `ERROR`, `STALL`, `TIMED_OUT` and `OVERFLOW` all to `EPIPE`, even though libusb distinguishes them. **DESIGN:** establish faithful mappings and tests; do not inherit another userspace exporter's simplification as the Linux protocol requirement.
- Wrapped-FD import attempts every active interface, detaches drivers, and resets alternate settings to zero; the inspected alternate-setting initialization does not check the return value before updating bookkeeping. **DESIGN:** account for failures, multiple interface numbers and global effects; restrict admission to honestly supported profiles rather than guessing state.
- Disconnect cancels outstanding transfers, waits ten seconds, then waits without a deadline for pending completions. This avoids freeing live callbacks, but it is not bounded shutdown. **DESIGN:** retain event servicing and define safe escalation if drain cannot finish; do not “fix” a timeout by freeing buffers or destroying their owner while callbacks may still execute.

Positive source evidence is useful but limited: the candidate has asynchronous libusb control/bulk/interrupt paths; wrapped-FD handling keeps external FD ownership; speed conversion explicitly distinguishes libusb versus Linux USB speed enums; endpoint/alternate-setting metadata is built from the active descriptor. This is not a complete parser/security audit, not NDK build evidence, and not full composite descriptor preservation proof. [H14, H15]

### 4.3 Concrete Rust physical-exporter gaps

Pinned `src/host.rs` performs synchronous transfers with one-second timeouts; the rusb interface handlers share a `Mutex<DeviceHandle<GlobalContext>>`. Several failed OUT calls are discarded with `.ok()` and execution returns `Ok(vec![])`; failed IN paths can also reach an empty successful response. `src/lib.rs` awaits a submitted operation inside the connection command loop, then returns OUT `actual_length` from requested `data.len()`. Its unlink branch logs `unlink_seqnum` and returns a response without canceling a stored in-flight native operation. The nusb construction hardcodes EP0 packet size 16, and both construction paths explicitly ignore alternate settings. [H16]

**DESIGN:** do not certify this physical path unchanged: it can serialize unrelated endpoints, delay processing cancellation, and lose error/actual-length information. This source evidence justifies using the independent CDC fixture for importer investigation while preferring the C++ candidate for the first carefully bounded Android experiment. It does not justify implementing a replacement USB/IP stack. The fixture still needs its own safe listener configuration, reviewed descriptors, and an actual bidirectional test workload; independent implementation is not an infallible oracle.

## 5. Production transport acceptance details

### 5.1 Descriptors, speed and EP0

**DOC/SOURCE:** USB/IP import metadata includes speed, active configuration and interface information, while USB control traffic carries descriptor requests. libusb's `libusb_get_device_speed` means negotiated connection speed, not `bcdUSB`. The C++ candidate correctly has an explicit speed-enum conversion; blind casts are unsafe for SuperSpeed enum values. [H01, H09, H15]

**DESIGN:** compare direct-device and guest-visible device/configuration/interface/endpoint/class-specific descriptors, including S3 CDC association/class descriptors and the Espressif JTAG capabilities request. Record real endpoint addresses, packet sizes, configuration, alternate settings, strings where available, and negotiated speed. Treat every length and count as untrusted. Never fabricate speed from USB-C connector shape, `bcdUSB`, or a convenient full-speed default. If a required fact is unavailable, use only a documented narrowly justified profile mapping and retain the uncertainty; do not publish generic support.

A virtual host assigning a device address is not permission to readdress Android's already enumerated physical device. Clear-halt, configuration, alternate setting and reset-like requests require explicit handling. Upstream Linux `stub_rx.c` handles these specially. libusb documents that reselecting the same configuration can reset endpoint/alternate state and that configuration changes cannot occur while interfaces are claimed. A native reset can invalidate the handle and require rediscovery. [H03, H09]

**DESIGN:** enumerate exact control requests observed for Linux attach, CDC open/line-state changes, esptool, OpenOCD and the external adapter. Distinguish USB port/bus reset, target CPU/JTAG reset, CDC DTR/RTS-driven boot entry, and firmware reboot/disappearance. They are different operations; supporting one proves none of the others. Check configuration/claim state after a global operation, invalidate old incarnation bindings after re-enumeration, and refuse unsupported operations without invented success. If required normal tools cannot operate with truthful behavior, the profile remains blocked.

### 5.2 Transfer ownership and cancellation

**DOC:** libusb cancellation is asynchronous; its completion callback must run before transfer/buffer reclamation. “It is undefined behaviour to free a transfer which has not completed.” Canceled or timed-out requests may already have transferred bytes. Synchronous libusb/event-processing operations must not be called recursively from an event callback. USB setup fields are little-endian, unlike USB/IP envelope fields. EP0 libusb buffers include an eight-byte setup prefix, but completion `actual_length` refers to data, not setup bytes. [H11]

**DOC:** Linux's USB/IP specification explicitly says a successfully unlinked submission has no corresponding `USBIP_RET_SUBMIT`. Its example uses `RET_UNLINK(-ECONNRESET)` for actual cancellation; unlink after a completed submit yields `RET_UNLINK(0)`. Therefore “nonzero means failure, zero means successfully canceled” is not a safe interpretation. [H01, H03]

**DESIGN acceptance corpus:** fragmented/coalesced stream; truncated/oversized headers and payloads; version/opcode errors; illegal endpoint/direction; setup/data-length mismatch; duplicate in-flight sequence numbers; unknown unlink target; submit failure; short IN; partial OUT; zero-length transfer and zero packet semantics; stall/clear-halt; timeout/disconnect; cancel-before-completion/cancel-after-completion; import exclusivity; two identical devices; teardown with active callbacks; and bounded queue/payload memory. Validate OUT completion from backend actual length, not the requested length. Reject unsupported modes with defined error/teardown behavior, not parser desynchronization.

Long-lived CDC IN and interrupt polls must not hold a device-wide blocking I/O mutex or prevent JTAG OUT/IN progress. The outer share is whole-device exclusive, but guest drivers/tools may concurrently own separate interfaces. Serial monitor and serial flasher still compete for the same serial function; configuration/reset can affect all functions. Do not replay programming or reset traffic after a lost tunnel; report uncertain target state.

## 6. ESP32-S3 and independent external adapter

### 6.1 Native Serial/JTAG is a fixed composite controller

**DOC:** the current R91/R92/R93 `stable` pages identify as ESP-IDF **v6.1**. R91 explicitly lists bidirectional console, esptool/`idf.py flash`, and “JTAG debugging, performed simultaneously with serial operations.” It calls the controller fixed-function hardware, unlike firmware USB-OTG/TinyUSB. The D−/D+ pins are GPIO19/GPIO20; exact board connector/schematic still governs the physical test. A separate CP210x/CH34x USB-UART connector is not evidence of native JTAG. [H22–H24]

**DOC:** the internal PHY is shared between USB-OTG and USB-Serial-JTAG; the ESP-USB guide says only one of those controllers can use it at a time. Its concurrent OTG/Serial-JTAG route requires an external PHY. That is distinct from native CDC+JTAG concurrency, which is documented. Do not modify security/debug eFuses to force a transport experiment; select appropriate test hardware/controller mode instead. [H25]

**SOURCE:** `interface/esp_usb_jtag.cfg` uses `adapter driver esp_usb_jtag`, VID/PID `303a:1001`, capabilities descriptor `0x2000`, and JTAG transport; `board/esp32s3-builtin.cfg` composes it with `target/esp32s3.cfg`. VID/PID is a discovery clue, not unique identity. The configuration's 40000 kHz adapter setting is not a measured USB/IP performance promise. Pin a matched ESP-IDF, Espressif OpenOCD, target GDB and extension installation; don't assume generic Debian OpenOCD contains the required backend. [H26, H27]

**DESIGN:** source-level debug chain remains stock workbench → guest extension/debug adapter → guest target-architecture GDB → guest OpenOCD/libusb → imported USB device. An Android-hosted OpenOCD plus GDB TCP tunnel does not satisfy this default topology. The guest CPU ISA and Xtensa target ISA are different dimensions; native extension/tool binaries must match the actual guest architecture.

### 6.2 Concurrency and recovery conditions

**DOC:** R91 says main USB Serial/JTAG console configuration is needed for input/REPL; secondary console configuration is an output path. Deep sleep disconnects the device, while light sleep can leave it unresponsive without re-enumeration until physical reconnect. Firmware can disable the controller or reconfigure pins; documented recovery involves boot-mode/reset actions. The console has buffering behavior, including a possible one-time 50 ms wait, and firmware flush behavior. [H22]

**DESIGN certification:** use known firmware that supports bidirectional console and retains native controller ownership. Show overlapping serial traffic and JTAG halt/resume/breakpoint activity, not two sequential demonstrations. While the CPU is halted, absent firmware-generated logs are expected; prove transport health before/after resume and independent endpoint activity instead of requiring impossible continued application execution. Separately test serial monitor handoff to esptool, authorized flash/verification, debug attach/detach, ordinary reset, sleep, cable loss, app/service death, tunnel/VM loss and reconnect without stale identity or replay.

### 6.3 External adapter is a separate mandatory profile

**DOC:** Espressif's JTAG guide requires an external adapter compatible with target voltage and OpenOCD, and notes ESP32-S3 does **not** support SWD. S3 JTAG typically uses a 3.3 V domain; exact board/adapter documentation must supply wiring and voltage. A probe family name is not a compatibility guarantee. [H24]

**DESIGN:** U02.01 chooses an actually available independent adapter **and target**, records firmware, hardware revision, connector/pinout, voltage reference/power behavior, backend, raw-USB/HID requirements, guest ABI and license. Examples of distinct profiles include CMSIS-DAP HID versus bulk, FTDI MPSSE versus UART-only, ST-Link with a supported target, and vendor FPGA cables. An external SWD probe may satisfy the external requirement with its own supported target; it cannot be assumed to debug the S3. Built-in S3 JTAG controls that chip, not another board. Do not infer JTAG merely because an external FTDI serial node exists.

Pass requires normal Linux-tool discovery as a non-root user, controlled target identification, meaningful approved programming/debug operation, verification and detach/reconnect through the same production USB/IP route. Choose a reversible expendable test fixture; no guessed wiring, security-fuse modification, proprietary-driver substitution or unsupported architecture claim.

### 6.4 Optional serial work remains optional and narrower

**DOC:** pySerial distinguishes RFC2217 control negotiation from byte-only `socket://`; neither provides authentication/encryption. esptool remote-port documentation now expressly says native USB-OTG and USB-Serial-JTAG are unsupported via those remote URLs because esptool cannot inspect the local USB IDs it uses for native behavior. [H28, H29]

**DESIGN:** keep API-37 serial backend work, `usb-serial-for-android`, RFC2217, PTY/CUSE and process-scoped libusb shims off the default dependency path. They are separate, explicitly reduced-scope profiles. For optional RFC2217, select an actual UART bridge/target, verify its control-line/reset behavior and pinned esptool syntax, and certify monitoring and uploading separately. Neither a successful remote flash through UART nor fake discovery metadata certifies native S3 USB/IP/JTAG.

## 8. Test and authority boundaries

- **Read-only/source:** this report, remote code inspection, kernel/config inventory. No target success implied.
- **Synthetic integration:** reviewed CDC fixture on a real guest kernel. Requires explicit authorization for module loads/imports; no keyboard/storage injection. Synthetic traffic tests Linux import mechanics, not a physical S3.
- **Physical feasibility:** ordinary APK and actual Googlebook/board. Even esptool identification may reset or upload a RAM stub, and OpenOCD attach may halt/reset a target; they are not automatically read-only diagnostics. Obtain operation-appropriate approval.
- **Physical certification:** approved disposable firmware, verified target behavior, complete debug path, concurrent interfaces, external probe and failure recovery. Never burn eFuses or disable secure boot as a transport workaround.
